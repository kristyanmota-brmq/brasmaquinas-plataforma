## 1. Resumo executivo

A TOOL-003 elimina o **copy/paste manual** entre Claude Code (VS Code) e GPT (ChatGPT) durante o ciclo de revisão LLM pós-handoff, mantendo **dois comandos seguros e modulares** ao invés de um único comando de ponta a ponta:

1. `/handoff-claude-report TASK-XXX` — **já existente** (TOOL-001). Serializa o plano para `ai/claude-report.md` com preview + confirmação humana.
2. `/gpt-review TASK-XXX` — **novo nesta task**. Orquestra a chamada real à Responses API, validação estrutural e impressão de resumo executivo no terminal.

A separação preserva três garantias:

- **Segurança:** `/handoff-claude-report` continua exigindo preview + confirmação humana antes de gravar.
- **Modularidade:** `/gpt-review` aborta cedo se `ai/claude-report.md` estiver ausente, desatualizado ou com `task_id` divergente, evitando custo de API desperdiçado.
- **Reuso:** o CLI `print-review-summary.mjs` é testável standalone via `node:test` (7 cenários cobrindo aprovado, ausência, divergência, blockers, invariante violada, telemetria zerada, argumento ausente).

**Nenhum arquivo de produto (`src/**`) foi alterado.** **Nenhum secret foi exposto.** **Nenhuma invariante das 7 foi violada.** **Nenhuma aprovação humana foi automatizada.**

## 2. Componentes entregues

### 2.1 Comando `/gpt-review TASK-XXX`

Arquivo: `.claude/commands/gpt-review.md` (~100 linhas).

Sequência operacional (em ordem estrita):

1. **Valida argumento.** Aborta se `TASK-XXX` ausente.
2. **Valida `ai/current-task.md`.** Lê frontmatter; aborta se `task_id` divergente do argumento; aborta se `status` não estiver em `{em_planejamento, aguardando_revisao_gpt, aguardando_aprovacao_humana}`.
3. **Valida `ai/claude-report.md`.** Aborta se ausente; aborta se cabeçalho não citar `TASK-XXX`. Mensagem fixa em caso de falha:
   > "Handoff não pronto para TASK-XXX. Rode primeiro `/handoff-claude-report TASK-XXX` e depois `/gpt-review TASK-XXX`."
4. **Executa `node scripts/ai/run-gpt-review.mjs --task TASK-XXX`** (chamada real à Responses API). Sem retry automática.
5. **Executa `node scripts/ai/validate-structure.mjs --task TASK-XXX`** (read-only).
6. **Executa `node scripts/ai/print-review-summary.mjs --task TASK-XXX`** (novo CLI desta task).
7. **Imprime próxima ação humana** (texto fixo: ler gpt-review.md completo, calcular hash sha256, editar decision-log.md append-only, atualizar status, re-validar, só então `/implementar`).

Garantias gravadas no próprio comando:

- **NUNCA** edita `ai/decision-log.md`.
- **NUNCA** transita `ai/current-task.md.status`.
- **NUNCA** chama `/implementar`, `/fechar-task` nem cria commit/push.
- **NUNCA** chama `run-gpt-review.mjs` mais de uma vez por execução (custo).
- **SEMPRE** aborta cedo se pré-requisitos inconsistentes (evita custo desperdiçado).
- **SEMPRE** propaga exit code não-zero ao usuário.

### 2.2 CLI `scripts/ai/print-review-summary.mjs`

CLI puro Node sem dependências externas (~240 linhas).

- Lê `ai/gpt-review.md`, extrai JSON canônico via `extractStructuredBlock` de `scripts/ai/lib/parsers.mjs`.
- Valida `block.task_id === argv.task`.
- Lê `ai/current-task.md` apenas para obter `status_atual` (best-effort, não obrigatório).
- Deriva `override_permitido_derivado` via `deriveOverridePermitido` de `scripts/ai/lib/invariants.mjs` (regra terminal de invariante permanente).
- Imprime resumo executivo em caixa de texto plana (ASCII) com 11+ campos: `task_id`, `status_atual`, `veredito`, `recomendacao`, `blockers_count` + lista de IDs, `invariantes_violadas`, `override_permitido_declarado`, `override_permitido_derivado`, `tokens_prompt`, `tokens_completion`, `custo_estimado_usd`, `arquivo_completo`, `proxima_acao_humana`.
- Quando telemetria está zerada, imprime nota de limitação V1 inline.
- Próxima ação humana varia: invariante violada → "Reformular plano e voltar a /planejar"; veredito reprovado → "Decidir override em decision-log (risco assumido obrigatório) OU reformular"; demais → leitura + decision-log append-only.

**Exit codes:**

| Code | Significado |
|---|---|
| 0 | Sucesso (resumo impresso) |
| 2 | `task_id` em `gpt-review.md` ≠ `--task` argumento |
| 3 | `ai/gpt-review.md` não encontrado |
| 4 | Bloco JSON canônico inválido ou ausente |
| 5 | Argumento `--task` ausente |

**Não tem efeitos colaterais:** apenas LÊ arquivos e imprime no stdout. Não chama API, não edita arquivos, não altera status, não toca decision-log, não roda validate-structure internamente, não implementa, não commita, não faz push.

## 5. Limitações conhecidas (V1)

Herdadas da TOOL-002 e explicitamente documentadas:

1. **Telemetria de custo declarada pelo modelo, não capturada da API.** Os campos `tokens_prompt`, `tokens_completion` e `custo_estimado_usd` no JSON canônico vêm do próprio modelo (frequentemente zerados ou imprecisos). A **referência final de cobrança é o dashboard/fatura OpenAI**. Sugestão de captura real fica para TOOL-004 futura.
2. **Sem cap automático de custo** (`OPENAI_COST_CAP_USD`). Limite humano/manual mantido (≤ US$ 0,50 por execução). Cap automático = Fase 2 do roadmap TOOL-001.
3. **Sem retry automática** em caso de HTTP ≠ 200 ou erro de rede. O comando aborta com stderr e instrui o humano a investigar.
4. **Sem hooks automáticos** do Claude Code (`PostToolUse`, `Stop`). O fluxo permanece **invocado pelo humano** — Fase 2 do roadmap TOOL-001.

Essas limitações **não comprometem** a invariante de não-mascarar-pendência: estão visíveis no `ai/README.md`, no próprio `.claude/commands/gpt-review.md` e neste relatório.

## 8. Conflito de naming TOOL-003 — resolução

A TOOL-002 sugeriu, ao final do seu relatório, que o ID `TOOL-003` fosse atribuído à **captura real de `response.usage`** da Responses API. Posteriormente o briefing humano atribuiu `TOOL-003` à **orquestração single-command pós-handoff** (esta task).

**Resolução adotada:**

- `TOOL-003` (esta) = orquestração `/gpt-review` + CLI `print-review-summary.mjs`.
- `TOOL-004` (futura) = captura de `response.usage` real e cálculo de custo via tabela de preços por modelo.

Conflito registrado também no próprio arquivo da task (`tasks/TOOL-003-gpt-review-pos-handoff.md`) na seção "Rastreabilidade".
