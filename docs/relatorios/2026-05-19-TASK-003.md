## O que foi feito

### TASK-003 — Bloquear PDF quando há blockers ativos

Implementado o gate de governança que impede a geração de PDF de proposta final quando
`diagnostics.blockers` está não-vazio. A lógica de decisão foi extraída para uma função pura
testável; a rota responde com JSON estruturado; a UI diferencia erros técnicos de bloqueios
por pendência técnica.

**Arquivos criados:**

- `src/lib/layout/__tests__/pdf-guard.test.ts` — 3 testes unitários para `pdfEmissionBlockers`

**Arquivos modificados:**

- `src/lib/layout/irrigation-project.ts` — adicionada `pdfEmissionBlockers(result): string[]`,
  função pura exportada que retorna `result.diagnostics?.blockers ?? []`
- `src/app/api/projetos/[id]/pdf/route.tsx` — importa `pdfEmissionBlockers`; se
  `blockers.length > 0`, retorna HTTP 422 com `{ error: "PDF_BLOCKED", message, blockers }`
  antes de chamar `renderToBuffer`
- `src/components/map/ProjectMap.tsx` — estado `pdfError` tipado como discriminated union
  (`{ kind: "blocked"; blockers }` | `{ kind: "technical" }` | `null`);
  `handleExportPDF` trata `!res.ok` explicitamente, parseia o corpo JSON da resposta,
  seta `pdfError` sem tentar baixar blob; painel flutuante exibe mensagem diferenciada ao usuário
  com botão de fechar

## Decisões tomadas

| Decisão | Alternativa descartada | Motivo |
|---------|----------------------|--------|
| Rota retorna JSON `{error, message, blockers}` | Plain text | JSON permite ao cliente diferenciar tipo de erro programaticamente sem parsear string |
| Estado `pdfError` como discriminated union | `string \| null` | Distingue "bloqueio técnico" de "erro inesperado" sem condicionais frágeis no JSX |
| `!res.ok` tratado explicitamente antes do `catch` | Só no `catch` | HTTP 422 não lança exceção JS — seria silencioso sem tratamento explícito |
| `pdfEmissionBlockers` em `irrigation-project.ts` | Inline na rota | Função pura testável com vitest; rota Next.js é difícil de testar diretamente |
