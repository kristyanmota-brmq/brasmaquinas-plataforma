## 2. Adaptação durante a implementação (transparência)

O plano original previa fixtures "2/3/4 setores". Durante a leitura do código, descobri:

- [`src/lib/layout/layout-use-cases.ts:154`](../../src/lib/layout/layout-use-cases.ts#L154) define **`setoresCount: jornada`** literalmente.
- [`src/app/projetos/[id]/layout-schema.ts:89`](../../src/app/projetos/[id]/layout-schema.ts#L89) restringe `jornadaHoras: 9 | 14 | 21`.

**Conclusão:** `setoresCount ∈ {9, 14, 21}` no schema atual. Não há caminho para 2/3/4 sem alterar `src/` — fora do escopo Classe B.

Implementação retomada com novos nomes (`fixture-e06-9setores` etc.) e novos alvos. Cobertura semântica da TASK-014 (labels com múltiplos setores) mantida — apenas o range mudou.

## 4. Arquitetura do script

```
main()
 ├─ Verifica POSTGRES_PRISMA_URL ou DATABASE_URL no env
 ├─ Se --clean → cleanFixtures()
 │   ├─ prisma.project.deleteMany({ where: { id: { in: FIXTURE_IDS } } })
 │   └─ Sanity check: Projeto A continua existindo
 └─ Senão → seedFixtures()
     ├─ readProjectA() → projetoA (findUnique)
     ├─ snapshot = { id, updatedAt }
     ├─ ownerId, dataA, vazaoPorAspersor, tempoPorSetorMinutos
     ├─ resultA = calculateIrrigationProject(dataA)
     ├─ physicalColumns = resultA.physical.physicalColumns  // 31 cols no Projeto A
     ├─ Constrói 4 fixtures (1 blocker + 3 jornadas)
     ├─ Para cada fixture:
     │   ├─ r = calculateIrrigationProject(layout)
     │   ├─ assert(blocker presente se esperado)
     │   ├─ assert(setoresCount = jornada)
     │   ├─ assert(id ≠ Projeto A id)
     │   └─ prisma.project.upsert({ id, ... }) com data: ProjectLayout
     ├─ Re-lê Projeto A
     ├─ assert(updatedAt === snapshot.updatedAt) || ROLLBACK + exit(1)
     └─ findMany filtrado por ownerId + IDs whitelisted → confirma 4 visíveis
```

## 7. Limitações conhecidas

1. **Range de setores limitado a 9/14/21.** O schema atual não suporta outros valores. Para variar (ex.: cobrir 2-8 setores ou >21), seria necessário Classe A para estender o use case e o tipo literal de `jornadaHoras`.

2. **Polígono herdado do Projeto A.** Todos os fixtures usam o mesmo polígono (4,87 ha, Barreiras/BA) e os mesmos aspersores/laterais. Variação está apenas em `pump` ou `sectorization`. Para validar a UI com polígonos visualmente distintos, seria necessário gerar polígonos sintéticos no script (escopo maior, Classe A se importar geração de polígono via `turf`).

3. **DB local obrigatório.** Script depende de `POSTGRES_PRISMA_URL` configurada. Em ambientes sem DB Postgres, ele aborta com erro claro. Não há mock nem DB de teste — esses fixtures vivem no banco real do dev.

4. **Sem teste automatizado dedicado.** Validações são executadas inline no script (asserts em runtime). Não há teste Vitest para o seed. Para Classe B, validações documentadas + smoke test são suficientes; teste E2E do seed exigiria infra de DB de teste.
